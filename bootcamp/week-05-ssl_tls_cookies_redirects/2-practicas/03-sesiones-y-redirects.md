# Práctica 03 — Sesiones y redirects

> **Duración**: 50 min · **Entregables**: `sesion.md`, `redirects.md`

Vas a mantener una sesión con cookies a lo largo de varios comandos, ver cómo
se pierde una cookie en un redirect cuando el motor está apagado, proteger el
tarro, y después recorrer los redirects: seguirlos, cortarlos, ver cómo
cambian el método y comprobar qué credenciales viajan a otro host.

**Antes de empezar**, desde la raíz del repositorio:

```bash
./scripts/start.sh
export CA="$PWD/docs/lab-ca.pem"
mkdir -p ~/bc-curl-trabajo/semana-05/p3 && cd ~/bc-curl-trabajo/semana-05/p3
```

---

## Paso 1: La memoria que curl no tiene

**Por qué**: hay que ver que dos comandos curl no comparten nada antes de
entender para qué sirve el tarro.

**Comando**:

```bash
curl -s -o /dev/null -D - 'http://localhost:8080/cookies/set?sesion=abc' | grep -i '^set-cookie'
curl -s http://localhost:8080/cookies | jq -c .
```

**Verifica**:

```
Set-Cookie: sesion=abc; Path=/; HttpOnly
{"cookies":{}}
```

El servidor fijó la cookie; el segundo comando no la manda. Apunta en
`sesion.md` qué atributos trae el `Set-Cookie` y cuál falta para que sea una
cookie "de sesión".

---

## Paso 2: El motor y `-L`

**Por qué**: un login que fija la cookie y redirige es el caso más común. Con
`-L` solo, la cookie se pierde **dentro del mismo comando**.

**Comando**:

```bash
# /cookies/set fija la cookie y redirige a /cookies.
curl -sL 'http://localhost:8080/cookies/set?a=1' | jq -c .
curl -sL -b '' 'http://localhost:8080/cookies/set?a=1' | jq -c .
```

**Verifica**:

```
{"cookies":{}}
{"cookies":{"a":"1"}}
```

Apunta en `sesion.md` qué hace `-b ''` si no manda ninguna cookie.

---

## Paso 3: Una sesión en tres comandos

**Por qué**: es el patrón completo, y el que usa el proyecto.

**Comando**:

```bash
(umask 077 && : > tarro.txt)

# Login.
curl -s -b tarro.txt -c tarro.txt 'http://localhost:8080/cookies/set?sesion=abc&tema=oscuro' -o /dev/null
# Uso.
curl -s -b tarro.txt -c tarro.txt http://localhost:8080/cookies | jq -c .
# Logout parcial: el servidor borra "tema".
curl -s -b tarro.txt -c tarro.txt 'http://localhost:8080/cookies/delete?tema' -o /dev/null
curl -s -b tarro.txt http://localhost:8080/cookies | jq -c .
```

**Verifica**:

```
{"cookies":{"sesion":"abc","tema":"oscuro"}}
{"cookies":{"sesion":"abc"}}
```

Apunta en `sesion.md` qué pasaría si usaras solo `-c` en el segundo comando
(sin `-b`), y solo `-b` en el tercero (sin `-c`).

---

## Paso 4: Leer el tarro

**Por qué**: el formato tiene una trampa que se lleva por delante las cookies
importantes.

**Comando**:

```bash
cat tarro.txt
echo '--- grep -v "^#":'
grep -v '^#' tarro.txt | grep -c .
echo '--- awk NF==7:'
awk -F'\t' 'NF == 7 { print $1, $5, $6 "=" $7 }' tarro.txt
```

**Verifica**:

```
# Netscape HTTP Cookie File
# https://curl.se/docs/http-cookies.html
# This file was generated by libcurl! Edit at your own risk.

#HttpOnly_localhost	FALSE	/	FALSE	0	sesion	abc
--- grep -v "^#":
0
--- awk NF==7:
#HttpOnly_localhost 0 sesion=abc
```

Apunta en `sesion.md` por qué el `grep -v '^#'` dice que no hay cookies, y
qué significa el `0` de la columna 5.

---

## Paso 5: Los permisos del tarro

**Por qué**: un tarro con 644 es una sesión que cualquier usuario del equipo
puede copiar. Hay que ver cómo lo crea curl y cómo lo respeta.

**Comando**:

```bash
curl -s -c nuevo.txt 'http://localhost:8080/cookies/set?s=1' -o /dev/null
stat -c '%a %n' nuevo.txt tarro.txt

# Reescribir el tarro protegido: ¿conserva los permisos?
curl -s -b tarro.txt -c tarro.txt 'http://localhost:8080/cookies/set?otra=1' -o /dev/null
stat -c '%a %n' tarro.txt
rm nuevo.txt
```

**Verifica**:

```
644 nuevo.txt
600 tarro.txt
600 tarro.txt
```

En macOS, `stat -f '%Lp %N'`. Apunta en `sesion.md` cómo crea el proyecto el
tarro para que nunca tenga 644.

## Paso 6: Cookies de sesión y `-j`

**Por qué**: curl guarda para siempre las cookies que un navegador tiraría al
cerrarse. `-j` simula "abrir el navegador de nuevo".

**Comando**:

```bash
# Una cookie con caducidad, ademas de las de sesion.
curl -s -b tarro.txt -c tarro.txt \
  'http://localhost:8080/response-headers?Set-Cookie=recuerdame%3D1%3B%20Max-Age%3D600' -o /dev/null
curl -s -b tarro.txt http://localhost:8080/cookies | jq -c .
curl -s -j -b tarro.txt http://localhost:8080/cookies | jq -c .
```

**Verifica**:

```
{"cookies":{"otra":"1","recuerdame":"1","sesion":"abc"}}
{"cookies":{"recuerdame":"1"}}
```

Apunta en `sesion.md` para qué prueba usarías `-j`.

## Paso 7: Ver un redirect sin seguirlo

**Por qué**: antes de seguir un salto, conviene saber a dónde va.

**Comando**:

```bash
curl -s -o /dev/null -w '%{http_code} -> %{redirect_url}\n' http://localhost:8080/redirect/3
curl -sL -o /dev/null -w '%{http_code} saltos=%{num_redirects} final=%{url_effective}\n' \
  http://localhost:8080/redirect/3
curl -sL --max-redirs 2 -o /dev/null http://localhost:8080/redirect/3; echo "max 2: $?"
```

**Verifica**:

```
302 -> http://localhost:8080/relative-redirect/2
200 saltos=3 final=http://localhost:8080/get
max 2: 47
```

Apunta en `redirects.md` cuántos saltos sigue curl 7.81 si no le pones
`--max-redirs`, y por qué no quieres ese valor.

## Paso 8: El método tras el salto

**Por qué**: es la trampa que convierte un POST en un GET sin avisar.

**Comando**:

```bash
U='http://localhost:8080/redirect-to?url=/anything&status_code'
for c in 301 302 303 307 308; do
  printf '%s: ' "$c"
  curl -sL -d dato=1 "$U=$c" | jq -c '[.method, .form]'
done
printf -- '-X POST + 303: '; curl -sL -X POST -d dato=1 "$U=303" | jq -c '[.method, .form]'
printf -- '--post302: '; curl -sL --post302 -d dato=1 "$U=302" | jq -c '[.method, .form]'
```

**Verifica**:

```
301: ["GET",{}]
302: ["GET",{}]
303: ["GET",{}]
307: ["POST",{"dato":["1"]}]
308: ["POST",{"dato":["1"]}]
-X POST + 303: ["POST",{"dato":["1"]}]
--post302: ["POST",{"dato":["1"]}]
```

Apunta en `redirects.md` una tabla con los cinco códigos: qué hace curl con
el método y con el cuerpo. Y por qué `-X POST` con `-L` es casi siempre un
error.

## Paso 9: ¿Qué credenciales viajan a otro host?

**Por qué**: curl quita algunas credenciales al cambiar de host, pero no
todas. Es lo que decide si el proyecto puede seguir redirects con una API
key.

**Comando**:

```bash
# Para curl, localhost y 127.0.0.1 son hosts distintos.
OTRO='http://localhost:8080/redirect-to?url=http://127.0.0.1:8080/headers'
MISMO='http://localhost:8080/redirect-to?url=/headers'

# Credenciales de prueba en un --config con 600, como hace el toolkit.
(umask 077 && printf 'header = "X-API-Key: clave-de-prueba"\n' > clave.cfg)
(umask 077 && printf 'user = "ana:pw"\n' > user.cfg)

printf 'basic, mismo host: ';  curl -sL --config user.cfg "$MISMO" | jq -c '.headers.Authorization'
printf 'basic, otro host: ';   curl -sL --config user.cfg "$OTRO"  | jq -c '.headers.Authorization'
printf 'api key, otro host: '; curl -sL --config clave.cfg "$OTRO" | jq -c '.headers["X-Api-Key"]'
printf 'trusted, otro host: '; curl -sL --location-trusted --config user.cfg "$OTRO" | jq -c '.headers.Authorization'
rm clave.cfg user.cfg
```

**Verifica**:

```
basic, mismo host: ["Basic YW5hOnB3"]
basic, otro host: null
api key, otro host: ["clave-de-prueba"]
trusted, otro host: ["Basic YW5hOnB3"]
```

Apunta en `redirects.md` qué haría tu script si el servidor de la API
redirigiera a un dominio que no controla, con cada uno de los tres modos de
autenticación del toolkit.

## Paso 10: No bajar de HTTPS

**Por qué**: un salto a `http://` desde `https://` manda la siguiente
petición en claro, con sus cookies.

**Comando**:

```bash
ABAJO='https://localhost:8443/redirect-to?url=http://localhost:8080/get'
curl -sL --cacert "$CA" -o /dev/null -w 'sin limite: %{url_effective}\n' "$ABAJO"
curl -sSL --cacert "$CA" --proto-redir '=https' -o /dev/null "$ABAJO"; echo "con =https: $?"
curl -sL --cacert "$CA" --proto-redir '=https' -o /dev/null -w 'https a https: %{url_effective}\n' \
  https://localhost:8443/redirect/2
```

**Verifica**:

```
sin limite: http://localhost:8080/get
curl: (1) Protocol "http" not supported or disabled in libcurl
con =https: 1
https a https: https://localhost:8443/get
```

Si usas zsh, prueba también `--proto-redir =https` **sin comillas** y apunta
en `redirects.md` qué pasa y por qué.

## 🧯 Si algo sale mal

| Síntoma | Causa probable | Solución |
|---|---|---|
| El paso 3 no muestra cookies | El tarro no se creó o la URL no está entre comillas y el `&` se comió el resto | Comillas simples en todas las URLs con `?` |
| `zsh: no matches found` | zsh interpreta el `?` de la URL | Comillas simples alrededor de la URL |
| `zsh: https not found` | `=https` sin comillas en zsh | `'=https'` |
| El paso 6 muestra más cookies | Repetiste pasos y el tarro acumuló | `rm tarro.txt` y empieza en el paso 3 |
| `stat: illegal option -- c` | macOS | `stat -f '%Lp %N'` |
| El paso 9 da la clave también en "basic" | Usaste el mismo host en las dos URLs | `localhost` en la petición, `127.0.0.1` en el destino |
